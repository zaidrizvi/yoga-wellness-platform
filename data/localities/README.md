# Delhi locality catalog: source, limits and maintenance

Source: Delhi Revenue Department, [colony1.pdf](https://revenue.delhi.gov.in/sites/default/files/revenue/ereg/colony1.pdf). Retrieved for this local proposal on 25 October 2026. Source SHA-256: `1d94536494940f8fed339685193cf9b7aab22fdd735912a55fb23e0e27ec70e6`.

`delhi-revenue.json` preserves all **2,261 numbered source rows** as **2,258 distinct name/district records**. Repeated name/district entries retain every original serial in `source_keys`. Stable UUIDv5 identifiers derive from source URL + normalized name/district. The extractor verifies continuous, unique serial coverage and refuses unparsed rows. Whitespace introduced by PDF positioning is normalized; district split-letter artifacts are matched only to the source's known district labels. Source category letters are not used as service or qualification data.

This is a broad **historical Revenue colony catalog**, not an authoritative current comprehensive list of every Delhi neighborhood, subdivision, postal boundary or NCR locality. Its eight source groupings (CENTRAL, EAST, NORTH, NORTH-EAST, NORTH-WEST, SOUTH, SOUTH-WEST, WEST) are historical grouping labels, **not a representation of today's administrative districts**. It supplies no reliable locality-to-PIN mapping. Name spellings, missing/new neighborhoods, district labels and duplicate-name disambiguation require administrator review. There is no claim that this file covers all current Delhi NCT geography. New Delhi/NDMC and other omissions must be reviewed rather than invented.

The proposed catalog migration imports **unverified, inactive records only**. It creates no service areas, PINs, approvals, providers or bookings. Records become selectable for service filtering only after explicit administrative geographic verification, mapping to existing genuine active `service_areas`, and locality activation. A professional must separately have approval for **each active mapped service-area UUID**. Sharing a PIN or district name alone never grants another locality. Multiple service-area/PIN mappings per locality and duplicate names in different source groupings are supported. Delivery-area choice identifies the exact mapped routing record; postal codes remain internal and server-derived.

For postal verification consult [India Post's PIN directory](https://www.indiapost.gov.in/rti/pincodelist) and other current authoritative geographic/postal sources. Their existence is not evidence that any proposed mapping is correct. Do not infer a locality's PIN from a similarly named post office, postal prefix, browser position or district. This proposal contains **zero inferred postal mappings**.

Delhi NCT records use `IN-DL`. Future NCR catalog records can use distinct region codes; public Delhi discovery explicitly requires `IN-DL`. Gurugram, Noida, Faridabad and Ghaziabad must not be entered as Delhi NCT. Source-region classification remains a reviewed administrative responsibility.

Maintenance: retain the original source/hash and review new authoritative releases. `scripts/import-delhi-localities.py <source.pdf>` reproduces the local JSON and the **currently pending** catalog migration using the external `pypdf` extraction tool (not an app dependency). Once that migration is deployed, **do not rerun the extractor over its applied migration file**. Prepare a new additive import/diff with a new timestamp, preserving existing UUIDs/references, and review changes before deployment. Routine legitimate additions, corrected source attribution, verification and activation use `/admin/coverage/localities` with mandatory reason and audit. Existing service-area mappings are append-only; corrections require deactivation and a separately reviewed replacement rather than silent reference rewrites.
