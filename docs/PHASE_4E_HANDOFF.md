## Direct booking safeguards and limitations

The server obtains professional, service, current revision, price, duration and commercial fields from approved offering projections. The customer submits stable IDs, chosen time, a review hash, notes and explicit consent, never an authoritative price or role. The database verifies exact active locality mapping, address ownership and routing, revision/hash, service publication, professional/service approval, weekly schedule/time off and overlaps. It calls the existing request/proposal/agreement rules under the existing fulfillment lock and exclusion constraint. Failure rolls back the whole new request. Exact retries return the same booking; reusing a key with changed details is rejected. Agreement is already stored for unchanged direct terms, so the customer is not asked to agree again. The professional must still accept before confirmation.

Preferred starts must fit existing booking request windows and horizon; the existing request RPC also requires its window start to be in the future. This preserves existing behavior rather than widening same-day booking rules. Weekly public hours are indicative, not guaranteed slots. Only one appointment is scheduled per request; package description/session quantities do not issue purchased entitlements. A confirmed booking is never labeled paid.

The six new tables have RLS and authenticated admin SELECT policies; customer choice reads additionally require the owning customer. All writes use guarded functions. Private proposal/coverage/bundle helpers have no client EXECUTE permission. New SECURITY DEFINER functions have empty search paths and explicit ACLs. Public functions expose only allowlisted fields. Existing roles, first/last-admin protections, application approvals and Storage policies are unchanged.
